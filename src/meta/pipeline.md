# 📐 采集与评审规范

> 采集口径 · 评审门槛 · 落库规则
> 这页是**流水线的操作手册**，改规则改这里

---

## 一、流水线全貌

```
┌─────────────┐   ┌─────────────┐   ┌─────────────┐   ┌─────────────┐
│  ① 采集      │   │  ② 简报      │   │  ③ 归纳总结  │   │  ④ 评审      │
│  每日 07:00  │──▶│  每日 08:00  │──▶│  周/月      │──▶│  月度评审会  │
│  raw/*.json  │   │  briefings/  │   │  简报中完成  │   │ deliverables/│
└─────────────┘   └─────────────┘   └─────────────┘   └─────────────┘
```

**核心原则：评审只读简报，不读原始采集文件。** 这样保证每期评审的输入面可控，不会被当天几百条原始情报淹没。

## 二、采集规则

### ⭐ 文章七段式（2026-11-12 用户要求 · 所有域文档强制）

**每一篇域文档**（产业/政策/安全）必须包含以下七段，顺序固定、标题不可改：

| # | 段落 | 标题写法 | 必答内容 |
|---|---|---|---|
| 1 | **信源核实** | `## 一、信源核实` | 来源怎么找到的（搜索请求原文）、原始 URL、发布主体、发布/更新时间、采集时间 |
| 2 | **事实核查** | `## 二、事实核查` | 逐条列出关键数据点 → 核查方式 → 结论；标出**互相矛盾的数字**及原因 |
| 3 | **原文归档** | `## 三、原文归档（快照）` | 快照文件路径 + SHA256 + 抓取时间；关键原文摘录 |
| 4 | **概要提取** | `## 四、概要提取` | 3–5 条要点，每条一句话 |
| 5 | **主要观点** | `## 五、主要观点` | 原文/作者的核心主张（**分开写"原文说"和"我的判断"**） |
| 6 | **参考意义** | `## 六、参考意义` | 对我方的意义：**按本阶段五方向（网络安全/信创/等保/隐私保护/护网）判定要不要转评审**；产品线级关联本阶段不写 |
| 7 | **总结输出** | `## 七、总结输出` | 一句话结论 + 落地去向勾选（产品特性/需求变更/专项整改，**本阶段以方向级产物为主**） |

**执行要点**：

- 第 1 段的"来源请求"要写**实际用的搜索词**，不是编一个 —— 这是为了让别人能复现同样的检索
- 第 2 段是**最容易被糊弄的一段**：数字必须逐条核，**发现矛盾就写明矛盾**，不要挑一个顺眼的用
- 第 3 段的快照由 `scripts/snapshot.py` 生成，**正文与 SHA256 必须真实**，不能手写
- 快照脚本已支持 **PDF 原文**（自动识别 `%PDF` 文件头并用 `pypdf` 提取正文，SHA256 仍对原始字节计算）；
  期刊/白皮书类情报**优先抓 PDF 正式版**而非公众号转载版 —— 转载版常删作者单位、文献编号与英文摘要
- 第 5 段必须区分「原文主张」与「我方判断」—— 混在一起等于把媒体观点当成结论
- 第 7 段的勾选必须与[评审四关](#三评审门槛)一致，不许直接勾上

### 每条原始情报的最小字段

采集脚本产出的每条记录**必须**包含这 8 个字段，缺字段直接丢弃：

| 字段 | 说明 |
|---|---|
| `id` | 稳定唯一 ID |
| `domain` | `solar` / `policy` / `security` |
| `title` | 一句话标题 |
| `source_url` | 原始链接（**必填**，无链接不入库） |
| `published_at` | 发布日期 |
| `collected_at` | 采集时间 |
| `summary` | 2–3 句摘要 |
| `relevance` | 与我方的关联说明（**必填**，写不出就说明不相关） |

### 三级分类（入库时定级）

| 级别 | 判据 | 后续处理 |
|---|---|---|
| 🔴 强约束 / 高危 | 直接约束我方功能或打在我方暴露面上 | 进日���的"需立即关注"段 |
| 🟡 有影响 | 改变经营参数或预期 | 进日报常规段 |
| ⚪ 备案 | 行业背景 | 只进"背景噪声"段，定期复查 |

### 去重

同一事件多次抓到 → 按 `source_url` 归一，保留**发布时间最新**的一条，更新 `last_seen_at`。

## 三、评审门槛

见 [评审输出](../deliverables/README.md) 的四关。核心一条：

> **"可能会影响"不算影响，必须能指名道姓说出我方哪个系统、哪个接口。**

### ⭐ 评审意见走 GitHub issue（2026-11-12 起 · 用户明确）

**一条评审意见 = 一个 issue。** 意见收齐后结合意见更新文档，然后统一 close。

| 项 | 规定 |
|---|---|
| **提 issue 的对象** | **评审意见 / 待决问题**，不是 bug 报告 |
| **一条 issue** | 只问**一个**问题；有多个问题就开多个 issue |
| **固定格式** | 背景（事实 + 出处）→ 问题（只问一个）→ 选项（含倾向 + 理由）→ 影响面 → 关联文档 |
| **标签** | `评审问题` + 分类（`口径` / `产物` / `流程` / `内容` / `待核实`） |
| **模板** | `.github/ISSUE_TEMPLATE/review-question.yml`（空白 issue 已关闭，防止走偏格式） |
| **收齐判定** | 每个批次的**待决清单**里全部 issue 关闭或标注"按默认"即视为收齐 |
| **回写** | 结论落定 → 更新对应文档 → issue 正文注明"结论已落 X 文档" → close |

**为什么走 issue**：评审意见散在聊天里，文档更新后没人知道哪条意见已被消化；issue 有唯一编号、可挂文档、可追溯，且**意见与结论一一对应**，不会出现"改了文档但没人知道为什么改"。

**提问纪律**：
- 每个 issue 必须给出**至少两个选项 + 倾向 + 理由** —— 只有问题没有选项的 issue 无法被高效回答
- 必须写明**影响面**（会改哪些文件）—— 让提 issue 的人自己先想清楚后果
- 我方现状不可查的，写成"待核实"类 issue，**不要在 issue 里替我方现状下结论**

### ⭐ 本阶段口径（2026-11-12 起 · 用户明确）

**转评审只走五个方向，暂不精到具体产品。**

| 项 | 规定 |
|---|---|
| **转评审方向** | 网络安全 · 信创 · 等保 · 隐私保护 · 护网 —— 只这五个 |
| **产品级归属** | **暂不要求**。库内尚无各产品线"特性 / 功能 / 应用场景"的结构化材料，凭情报做产品对应会失真 |
| **本阶段产物形态** | **方向级**：基线 / 覆盖度 / 差距清单 / 演练场景 / 观察台账 —— 不落产品功能改造 |
| **产品线级产物** | 一律标 🟡 **待复核**，不进排期；待产品材料积累后复核再定 |
| **暴露面纪律不变** | 方向级 ≠ 放宽第 1 关。仍须有**我方侧一手证据**（内部观测 / 资产清单 / 公开披露），不接受"可能影响我方" |

**为什么这么定**：情报到产品的最后一跳需要"产品特性 + 应用场景"材料，库内目前没有这层。硬做对应会产出看似具体、实则失真的动作 —— 宁可停在方向级，等材料到了再下沉。

**变更生效日期**：2026-11-12（首期评审已按此口径执行）

## 四、落库规则

### 文件命名

| 类型 | 规范 | 示例 |
|---|---|---|
| 采集原文 | CamelCase + 域名 | `componentPriceTrend.md` / `nDRC电价机制2026.md` |
| 简报 | `YYYY-MM-DD-daily.md` / `YYYY-Www-weekly.md` / `YYYY-MM-monthly.md` | `2026-11-12-daily.md` |
| 产物 | `<类型>-<主题>-<YYYYMMDD>.md` | `feature-priceForecast-20261115.md` |

**禁止**：中文文件名、带空格、以数字开头。

### 目录归属

| 内容 | 放哪 |
|---|---|
| 产业情报原文 | `src/solar-industry/` |
| 政策原文与解读 | `src/policy/` |
| 安全情报原文 | `src/security-intel/` |
| 简报 | `src/briefings/` |
| 评审产物 | `src/deliverables/` |
| 采集原始数据（不入 mdbook） | `raw/`（gitignore） |

### 写作规范

- 中文为主，技术术语保留英文
- 表格优先于长段落
- 标题层级不跳级（mdbook 要求）
- 每篇末尾有"参考链接"节

## 五、发布流程

```bash
cd pv-intel
git add -A
git commit -m "briefing: YYYY-MM-DD 日报"
git push origin main
```

- 禁止 force push
- 每次发布后 mdbook workflow 自动部署到 GitHub Pages

## 六、调整这条流水线时

改口径 → 改本文件 → 同步改采集脚本 → 在简报里注明变更生效日期。

**口径和实现必须一致**，否则简报里的说法和实际采集的内容对不上，整条流水线失去信任。
