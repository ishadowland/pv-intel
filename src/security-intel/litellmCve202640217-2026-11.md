## 四、概要提取

- ⭐⭐⭐ **CISA 于 2026-11-18 收录 KEV（期限 2026-12-02）**，CWE-**420 未受保护的备用通道**：正则源码过滤可被"字节码改写"绕过 → 在代理进程内执行任意代码，**默认 Docker 镜像中该进程以 root 运行 → uid=0**。
- ⭐⭐⭐ **比 CVE 本身更危险的是第二条链：无 CVE、无 advisory 的 `/key/regenerate` `user_id` 重绑定** —— **任意非管理员虚拟密钥可把自己指向管理员用户行、成为 PROXY_ADMIN**；修于 PR `#27793`/`#27819`，首发 **v1.84.0**（5 月 14 日）与 **v1.85.0**（5 月 17 日）。
- ⭐⭐⭐ **修复版本存在陷阱，打 CVE 补丁不够**：① 厂商公告自相矛盾（正文写 1.83.11、自身字段写 ≥1.83.10）→ 统一取 **≥1.83.11**；② **即使升到 1.83.11，重绑定仍然开着** → **真正的安全基线是 ≥1.84.0**（当期版本 11-19 为 1.110.1）；③ **镜像必须按 digest 固定** —— `v1.83.10-stable` 镜像在补丁后被重建过，**同一 tag 指向过不同内容**。
- ⭐⭐⭐ **攻击链六步的每一环都绕过了字面匹配**：`str.mro()` → 生成器 `gi_code` → 字符串拼接躲正则 → **`code.replace(co_names=...)` 改写名字表** → 从 `http_get.__globals__` 取真实 `__import__` → `os.popen("id")`。**源码里不含任何被禁词，运行时却能取到被禁对象。**
- ⭐⭐⭐ **根因是防护组合本身的失效**：`validate_custom_code` 是**对源码文本**的正则黑名单，而 `exec_globals["__builtins__"] = {}` **没有移除沙箱主动塞进去的原语**（`http_get` 等），**那些原语的 `__globals__` 仍指向未受限的模块命名空间**。
- ⭐⭐ **LiteLLM 1.107.0 本身被指为含恶意软件的版本（10 月 21 日分发）** → 与库内 11-20 记的 `agent-framework` 恶意版（1.26.1/1.26.2，10 月 21 日后）**同属 10 月下旬同一类事件**。⚠️ **本条在库内仅 itdef 一个来源 → 登记为"待第二源核实的供应链投毒指控"，不得当作已核实事实**。
- ⭐⭐ **暴露面判定条件三条**：① **是否以代理（server）方式运行**（仅作库调用不受影响）；② **是否启用自定义代码护栏**；③ **代理是否互联网可达**。
- ⭐⭐ **蜜罐观测（Zenity，4/15–5/24）**：569 次 POST `/guardrails/test_custom_code`、47 个猜测的 master key、64 个空 header 请求、一次 520 个相同 `{'probe':1}` 的批量能力探测 → **攻击面在被主动扫描，且攻击者在猜默认密钥**。
- ⭐ **在野利用证据来自 Google Threat Intelligence Group 的 LLMjacking 报告**（KEV 据此收录）；**无受害组织数，不得写"大规模在野利用"**。
- ⚠️ **EPSS 两源冲突（61.9% vs 17.0%）**，相差 3.6 倍，须并列不取均值。
- ⚠️ **我方无 LiteLLM 使用证据** → 不得下"我方受影响"结论。

## 五、主要观点

**原文主张**

- **CISA 官方**："allows remote attackers to execute arbitrary code via **bytecode rewriting** at the `/guardrails/test_custom_code` URI"；分类为"unprotected alternate channel"。
- **Corgea**："LiteLLM's advisory text says 'Fixed in 1.83.11', but its own patched-version field says >= 1.83.10…"；"Chained, they go from a **leaked inference key to root on the gateway**"；"**Being on 1.83.10 + closes the CVE but leaves the rebind open.**"
- **itdef**："**10 月 21 日分发的 1.107.0 含有恶意软件**"；"该缺陷涉及**代理上的** `POST /guardrails/test_custom_code`。**仅将 LiteLLM 作为库使用，与运行代理（服务器）不同**"；"如果代理本身没有暴露在互联网上"；"默认 Docker 镜像中代理以 **root** 身份运行"。
- **Zenity（经 vulnbrief 转述）**：蜜罐四个月记录 569 次探测、47 个猜测 master key、520 次批量能力探测；"The absence of a known gadget chain… is not a safe reason to defer patching"（同类表述）。

**我方判断**

- ⭐⭐⭐ **这条给我方最重要的东西不是"又一个 CVE"，而是它把库内 11-20 刚建立的"被偷的是身份不是密钥"结论，从个案升级成了可操作的架构原则 —— 而且它同时给出了反面教材：同一产品上"修了 CVE"与"漏洞已闭合"是两件事**。`/key/regenerate` 的本质是**"任何持有密钥的主体都能自行把身份重绑定到更高权限"** —— 这就是"偷身份不偷密钥"的字面实现：**攻击者拿到的仍是一把普通推理密钥，但可以让它"变成"管理员**。⭐⭐ **由此可以提炼出一条对我方产品与运维都直接适用的原则：任何"持有低权限凭据即可自行提升权限"的自助式接口，都是身份边界上的缺口**，而不只是一个 bug。** 我方若在自研系统里提供了类似的"自助修改绑定关系/自助提升配额"接口，**应当按这条处理**。
- ⭐⭐⭐ **"打上 CVE 补丁 ≠ 漏洞已闭合"这条，是库内至今最值得单独立一条基线的一条**。库内 11-20 刚在 `agent-framework` 条目里写过同类的话（"**'重装一遍'不是修复手段**"、**"缓存不清等于没修"**），但那说的是**同一产品同一版本内的多重残留**。LiteLLM 更进一步：**两条独立的漏洞链，修复版本区间不重叠**（CVE 修于 1.83.10/1.83.11，重绑定修于 1.84.0/1.85.0），**中间存在一个"打了 CVE 补丁但重绑定仍开"的版本窗口**。⭐⭐ **我方库的版本基线管理必须因此增加一个字段：每个组件要同时登记"CVE 修复版本"与"其它同名/异名漏洞修复版本"，并取其最大值作为基线** —— 否则用单条 CVE 的修复号做准入判断，会放行一批"打了补丁但仍有洞"的版本。⚠️ **而更隐蔽的一层是：重绑定这条链没有 CVE 号、没有 GHSA、不会被任何扫描器命中** → **我方的组件清单工具天然看不见它**。这与库内 11-19 已记的 Java4Shell "**SCA/SBOM 对运行时层漏洞完全失效**"是同一族问题的第三种形态（组件版本可见 / 运行时不可见 / **无编号漏洞不可见**）。
- ⭐⭐⭐ **"正则黑名单 + 清空 builtins"这套组合防护必然失效"这一条，直接命中我方 WAF 侧的既有争议**。库内 11-17 已记 `m_php_unserialize` 规则、11-19 已记 `rule_whitelist_fastpath`（**只看规则名/注释里的白名单关键词、不看载荷**）、11-20 已记 Cloudflare 观测到扫描器"约 17 小时后把利用请求伪装成 Chrome UA" → **库内已经三次撞到"靠特征匹配判定"的同一堵墙**。**LiteLLM 这个案例给出的是墙的物理结构**：**当攻击者能控制"运行时构造的名字"时，任何对字面文本的匹配都可被绕过** —— 因为正则只看字面量，而 `str.mro()` / `gi_code` / 字符串拼接 / `code.replace(co_names=...)` 这些手法**在源码里不留下任何被禁词的痕迹**。⭐⭐ **对我方的直接含义是：WAF 侧的判定维度必须从"载荷里有没有危险词"升级为"请求行为是不是危险行为"** —— 具体到本条，就是**"对管理/调试类端点的 POST，尤其是携带可执行代码或代码片段特征的 multipart/form-data"**这类行为特征。⚠️ **但要诚实标注：这不是"特征匹配无用"，而是"仅靠字面特征不够"** —— 库内至今没有行为特征检测的落地证据，本条只是把需求讲清楚了。
- ⭐⭐⭐ **"LiteLLM 1.107.0 被指为含恶意软件"这条，是库内 AI 供应链线上的第二例，且与第一例在时间上几乎重叠**。库内 11-20 记的是 `agent-framework` 恶意版 1.26.1/1.26.2（**11 月 17 日 20:35/21:08 UTC 投放、约 21:30 下架**）；本条是 LiteLLM 1.107.0（**10 月 21 日分发**）。⭐⭐ **两条合起来说明"AI 生态包的供应链投毒"不是孤例，而是一个正在发生的类别**。⭐⭐ **但必须严格区分两件事**：**`agent-framework` 那条有 Wiz/ChainGuard 等多源与 PyPI 官方接口的一手核验（版本已被删除）**，而**LiteLLM 1.107.0 目前只有 itdef 一个来源**。⚠️ **我方不得把两者并列为"已核实"** —— 正确处置是**把 1.107.0 登记为"待第二源核实的指控"，并把它纳入"我方若使用 LiteLLM 则必须逐版本核对发行历史"的检查项**。这也正好呼应库内 11-20 已确立的"**依赖取件策略改为固定已审计版本 + 审计留痕**"这条建议 —— **当上游会悄悄投毒且悄悄下架时，"装最新版"就是错的**。
- ⭐⭐ **"仅作库调用不受影响、运行代理才受影响"这个区分，正是我方暴露面自查缺的那种粒度**。库内 11-16 已记的德国 BSI-CS 154 要求建立"**联网资产与通信接口清单**"、库内 11-19 已记的 vCenter 案例给出"**可达 TCP 2012 即沦陷**"这类精确判定条件 —— **两者都在往"部署形态 × 可达性"的粒度走**。本条再加一条可套用的判定模板：**"同一产品在不同部署形态下的暴露面完全不同"**（库内 11-19 已记的 Expressway 案例"仅集群受影响、单机不受影响"是同一模板）。
- ⭐⭐ **"攻击者在猜默认 master key"（47 个不同猜测值）这条，对我方的直接含义是"默认密钥不是形式主义"**。库内 11-15 已记的凭据收割扫描器是"**攻击者去找 `.env` / `.git/config` / `phpinfo.php`"** —— 那是在找**泄露**的凭据；本条是**在猜**凭据。⭐⭐ **两者合起来说明：我方暴露面上"能猜到的默认凭据"与"被泄露的凭据"是两个独立的、同样要堵的口子**。库内 11-15 已记的"CISA 五部门联合警告"里的"**改默认口令**"这条措施，到今天仍然是独立且必要的一条。
- ⭐ **EPSS 冲突（61.9% vs 17.0%）不取均值，理由与库内 11-19 一致**：EPSS 每日更新，两源抓取时点不同即产生差异，**取均值会造出一个谁都没测过的数字**。正确做法是**两值并列 + 标注为"抓取时点不同"**。
- ⭐ **本条不产专项整改、不进产品改造** —— 我方无 LiteLLM。**它的价值在于给库内的三条既有结论各加一个案例、并给出一条新的版本基线管理原则**。

## 七、总结输出
