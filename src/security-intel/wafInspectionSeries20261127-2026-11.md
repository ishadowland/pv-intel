## 五、主要观点

**原文主张**

- SafeLine WAF 巡检报告（11-27 20:37 轮，v15.11）：9 个攻击源 IP；类型分布 🛡️ Threat Intelligence **9**；⭐ 需拉黑 **0** / ❌ 忽略 **9**；9 个 Threat Intelligence 走 fast-skip 默认忽略；白名单 **53** 个、本轮移除 **−3**；WAF 当前实际黑名单 **205** 个、本地备份 **396** 个（活跃 **205**、已删除 **191**）、本次新增 **0**、失败 **0**；今日新增合计 **4** 个 IP（1 个 Code Injection + 3 个 Info Leak，**均标注「本次窗口无命中」**）。
- fast-skip 机制原文：「按用户规则**默认不二次分析、不走 LLM、不拉黑、不推送**。SafeLine WAF 默认拦截即可」。

**我方判断**

- ⭐⭐⭐ **本期最该被纠正的，是库内连续三期形成的那个词：「归零」。** 库内 11-25 记「整轮归零（4 IP / 0 需拉黑 / 100% fast-skip）」并给出解释「**成因是我方侧无可见度**」；11-26 记「**连续两日归零被打破**」；11-27 日报又把「连续两日需拉黑归零被打破」写进了标题。**今天这份报告把这件事彻底讲清楚了**：**「需拉黑 0」统计的是「本轮 7 小时窗口内、需要二次分析的类型有多少」，而「今日新增 IP 列表」统计的是「当日所有被封禁的 IP」。这两者不是同一件事。** 本期最干净的证据是 **两个集合完全不相交** —— 今日新增的 4 个 IP（`43.138.102.124` / `3.249.231.44` / `35.231.113.102` / `66.132.172.134`）**一个都不在本轮 fast-skip 的 9 个里面**，而且报告自己写着它们「**本次窗口无命中**」。**所以本轮「需拉黑 0」的原因是：这 4 次攻击发生在 20:37 这一轮窗口之外，而不是没发生。** **结论必须改写为：「需拉黑 0」≠「当日无新攻击」≠「威胁停止」；正确读数是「本轮窗口内无新增可判定攻击，当日仍有 4 个 IP 被自动封禁」。** **建议把日报与台账里的措辞一律从「归零」改为「本轮窗口内需拉黑 0 / 当日新增 N」双读数，并要求两者同时出现 —— 单写任何一个都会误导。**
- ⭐⭐⭐ **「白名单 −3」是本期第二条必须照记、且必须忍住不解释的负结论。** 库内从 11-24 就在记「白名单 56 ±0，连续四期零变化」，并明确写过「**零变化对一个白名单来说既可能是『管理得当』也可能是『根本没人看』—— 库内无材料可判断是哪种，因此只能维持『待核实』**」。**今天它终于动了（56 → 53），但报告只写了「本轮移除 −3」，没有说移除了哪三个、谁移除的、依据是什么。** **所以今天比昨天更需要克制：变动本身不提供答案。** 它可能是「有人在清理过期白名单」（好），也可能是「有人误删/批量操作」（坏），也可能是「某个自动化流程在收缩」。**在拿到具体名单之前，「白名单管理是否到位」这个待核实项必须维持原判，不得因为「终于有变化了」就写成「开始有管理了」。** **同时这也让那条待办从「无法判断」升级为「必须去问」—— 下一步应直接取白名单备份文件做前后 diff，拿到被移除的 3 个 IP 与移除记录。**
- ⭐⭐ **黑名单基线 +4 恰好等于当日新增 4，这个一一对应关系把库内 11-26 的一个疑问彻底解开了。** 库内 11-26 记「活跃 196→201（+5）、总 387→392（+5）、已删除 191±0，新增全部来自活跃侧」，并提出疑问「**补录进来的 IP 是否应经过一次有效性复核**」。**今天的对照更清楚**：活跃 +4、总 +4、已删除 ±0，而当日新增恰好 4 个。** **这说明补录 IP 是直接写进活跃区的，完全绕开了「活跃 / 已删除」的回收流程** —— 也就是说，**一个已经不再攻击的 IP 也会长期留在活跃区，黑名单的「活跃」二字并不等于「近期活跃」。** **对 WAF 有效性判据的含义很直接：黑名单总规模（205）会单调偏大，而真正有意义的量是「当日新增」与「首次访问新 IP 进入量」。** 这与库内 11-26 已经立的判据（**有效性改用「首次访问的新 IP 进了多少」**）方向一致，今天补上了黑名单侧的证据。**
- ⭐⭐ **fast-skip 里 3/9 是黑名单存量 IP，这个比例今天首次被量化 —— 它把「忽略 ≠ 已处置」从定性变成了定量。** 库内 11-26 已记录「7 个里有 3 个已在黑名单」，今天是 9 个里有 3 个（33%）。**含义要说清楚：「忽略」在这个系统里的准确含义是「WAF 用威胁情报默认拦掉了，所以不需要再走 LLM 分析、不需要再拉黑、不需要推送」** —— **它是一个性能优化开关，不是一个处置结论。** **这 3 个 IP 之所以仍在到达，恰恰说明「已在黑名单」并不阻止请求到达我方站点。** **因此：**① **「需拉黑 0」在有 33% 黑名单存量 IP 的集合上出现，本身不构成任何有效性证据**；② **黑名单 IP 计数不能当作「我方挡住了多少」的指标**；③ 库内 11-16 记的「单 IP 黑名单覆盖度 ≈ 0（3,158 实例 / 92 网段）」与本期一致 —— **单 IP 封禁在这个威胁规模下本来就近乎无效，今天的 33% 只是同一结论的另一个切面。**
- ⭐⭐ **`collect.py` 本期暴露的是一个此前没被记录过的解析缺陷，比「字段缺失」更值得修。** 库内 11-26 记的六字段缺口是「少取字段」；**今天是「取错了集合」** —— 输出 `{"🛡️": 9}` 明显只统计了 fast-skip 那 9 个 IP，**把「今日新增 IP 列表」里的 Info Leak ×3 与 Code Injection ×1 完全丢掉了**。**后果很实际：如果我方每天拿这份 JSON 做趋势看板，那么「今日新增的攻击类型分布」这条最该看的曲线，恰恰是空的。** **修复成本极低（同一份报告的另一个小节），但必须写进采集管线待办。** 同时**「本期无判定级条目」要照记**：库内 11-26 曾出现 3 条判定级（`verdict` / `confidence` / `judge_model`），本期又回到了纯类型分布 → **说明那是波动，不是持续改善 → 不能把「上一期改善了」当成管线已修好的证据**。**这恰恰印证了本期 KEV 篇得到的同一个结论：不能基于单期观测下结论，要基于可重复的 diff。**
- ⭐⭐ **报告格式会回退这件事，本身就是一条方法论结论。** 库内 11-26 记「本期是格式跃迁」（URL / 规则 ID / 动作 / 站点 / 事件 ID / 报文全齐），我当时判断这让跨期对账成为可能。**今天这一轮，报告把这些字段全部丢了**（连 Info Leak 判定表都没有），退回 11-25 的形态。**这说明巡检脚本的输出格式是随内容浮动的，不是稳定契约。** **因此：我方不能建立「依赖某字段必存在」的自动化对账，必须把字段缺失当作正常情况处理。** **具体建议：跨期对账脚本必须先做「字段存在性检查」，缺字段时降级为「本期无法对账」并记录，不得用默认值补齐后当成可比数据。** 这条对 KEV 篇的「feed diff」也有同样的意义 —— **diff 之所以可靠，正是因为 feed 的字段是稳定的；报告不是。**
- ⭐⭐ **连续第二期没有我方站点命中记录，必须照记为负结论 —— 而这条负结论已经有它自己的方法论价值了。** 11-26 报告记录了两条命中兆瓦快链 `182.140.209.35:18443` 且 Deny；今天一条都没有。**但报告格式本期也退化了（无 URL / 站点 / 动作字段）→ 我方连「有没有命中我方站点」这个字段都查不到。** **库内 11-26 已写下的那句必须继续照记：「报告未记录 ≠ 我方零攻击」。** **今天它多了一个更硬的支点：不是「报告没记」，而是「报告已经不具备记录这个的能力」。** **这就是为什么库内 11-26 的那条待办（「用本期字段回填库内 11-15~11-18 命中记录做跨期对账」）至今仍是 P0 —— 因为字段随时会消失，任何一次成功抓到都必须立刻固化。**
- ⭐ **「连续第 3 期未复现」的负结论照记。** 巡检脚本「登录失败仍报 ok 但无报告落盘」缺陷，11-25、11-26、11-27 连续三轮均未复现，**但本库未取得这两天的其他轮次文件**（本库只拿到每天的第 5/5 轮）→ **未复现可能只是「没看到」，不是「没有」。** **并且，本库连续两期只拿到第 5/5 轮这件事本身就该记：巡检是每天 5 轮，而我方每天只入库 1 轮 —— 也就是说，我方对当日攻击的观测面本来就只有 1/5。** **这条应并入「WAF 有效性判据」一节：既然观测面只有 1/5，那么任何「本轮未见攻击」的结论，其强度上限只能是「本轮未见」。**
