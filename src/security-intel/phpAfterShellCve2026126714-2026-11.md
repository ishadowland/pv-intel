# phpAfterShell（CVE-2026-126714）：PHP 默认文件会话处理器非原子写入 → 免认证 RCE

> 🔴 强约束 · 采集于 2026-11-24 · 核心标识：**PHP 官方默认 `session.save_handler=files` 的会话文件更新是"先写后截断"两次非原子系统调用** → 写进程被中断即残留"新数据前缀 + 旧数据尾部"拼接文件 → 下一次 `session_start()` 把旧尾部当新记录反序列化 · ⭐⭐⭐ **CVSS v4.0 9.2（Critical）· 修复版 PHP 8.2.36 / 8.3.37 / 8.4.28 / 8.5.13 / 8.6.0** · ⭐⭐⭐ **10 月 21 日的 PHP2Shell 修复版（8.2.35 / 8.3.36 / 8.4.27 / 8.5.12）不修此漏洞 —— 已打过补丁的服务器仍然有洞** · ⭐⭐⭐ **入口是 `session.upload_progress`，即"任何能发 multipart 表单 POST 的页面"都是攻击面，与应用是否有上传功能无关** · ⭐⭐ **我方库内已有一条未闭环的同族待决项**（"我方 PHP 依赖清单 + `unserialize()` 入口清单 / 源站自查"🔴 仍未回填），且 11-15 已实测我方三站点命中 `/phpinfo.php`、11-17 已实测我方主站命中 PHP 反序列化规则 —— **本次把那条抽象待决项变成了一条有明确版本线与修复版的 CVE** · ⚠️ **截至 11-19 无在野利用报告、未入 CISA KEV、无公开武器化 PoC** · ⚠️ **不得下"我方受影响"结论**（我方 PHP 版本与会话配置库内不可查）

## 四、概要提取

- ⭐⭐⭐ **漏洞不在应用代码里，在 PHP 解释器的默认会话处理器里**：`files` 会话处理器用 `pwrite()` + `ftruncate()` 两次系统调用覆写会话文件，两次之间无原子性 —— 写进程被中断（OOM kill 等）就留下"新数据前缀 + 旧数据尾部"的拼接文件。
- ⭐⭐⭐ **会话格式无校验和、无文件级长度、无提交标记** → 攻击者在新数据里控制长度字段，就能让旧尾部里原本无害的字节被解码成一条新记录，其中可含被构造的序列化对象；下一次 `session_start()` 就把它反序列化出来。
- ⭐⭐⭐ **攻击入口是 `session.upload_progress`（PHP 内置上传进度回调）** → **应用不需要有上传功能**，任何能收 `multipart/form-data` POST 的 PHP 页面都是攻击面；且这一路径在脚本执行前就触发，**绕过了应用层登录检查**。
- ⭐⭐⭐ **10 月 21 日的 PHP2Shell 修复版不修此漏洞**（8.2.35 / 8.3.36 / 8.4.27 / 8.5.12 仍然有洞）→ **"已打补丁"这个状态在两条 CVE 下含义完全相反**，我方台账必须按版本号判定而非按"是否打过 10 月补丁"。
- ⭐⭐⭐ **修复版：8.2.36 / 8.3.37 / 8.4.28 / 8.5.13 / 8.6.0**；8.1 及更早 EOL 不再修，但官方 EOL 缓解分支（7.4/8.0/8.1）因回调直接 return 不受影响 —— **"未打补丁的老版本"仍保留原路径**。
- ⭐⭐⭐ **可利用性门槛极低**：变体 B（`pwrite()` 完成、`ftruncate()` 前终止）用 multipart 括号深度做时序控制，**24 次模拟命中率从 52.8% 提到 88.4%，一次全新 HTTP 运行 10 次即达目标状态**。
- ⭐⭐ **官方与发现方口径不一致**：官方公告称需要应用侧 gadget 链，发现方称其完整链**不依赖应用自定义 gadget 类**（改用 PHP 原生类内存破坏缺陷，细节仍在协调披露）→ **不得以"我方无 gadget 链"降级**。
- ⭐⭐ **缓解措施受限**：`session.upload_progress.enabled=0` 是 `INI_PERDIR`，**`ini_set()` 覆盖不了**；且官方与 CN-SEC 均明说"**关掉上传进度只去掉最易利用的入口，不消除缺陷本身**"；迁到 Redis/数据库会话后端不受此缺陷影响。
- ⭐⭐ **观测信号在主机侧，不在 WAF 侧**：multipart 上传伴随 PHP worker 异常崩溃/OOM kill + 会话目录畸形文件。
- ⚠️ **在野状态：截至 11-19 未报告在野利用、未入 CISA KEV、无公开武器化 PoC**（与库内已记的 PHP2Shell 已被在野利用不同，必须分开写）。

## 五、主要观点

**原文主张**

- **PHP 官方 GHSA**：受影响版本升级到对应分支的修复版；"As a temporary measure, disable `session.upload_progress.enabled` administratively if the feature is not needed, and limit the amount of untrusted data stored in sessions. Disabling upload progress removes the easiest path but does not fix the handler."
- **depthfirst**："The full chain does not depend on an application-defined gadget class."；并给出版本分析："The October builds (8.2.35, 8.3.36, 8.4.27, 8.5.12) truncate the file before writing, while 8.4.28RC1, 8.5.13RC1 and 8.6.0RC4 onward truncate after writing. depthfirst says that reordering moves the interruption window but **does not remove the retained-tail primitive**."
- **CN-SEC**："**10 月打过 PHP2Shell 补丁的服务器仍受影响**，必须再次升级。"；"**注意：这只是关闭最易利用的入口路径，并不消除缺陷本身**；应用若通过其他方式向会话写入攻击者可控数据，仍处于风险中。"；"在野状态：截至 11-19 未报告在野利用，未列入 CISA KEV；无公开武器化 PoC"；"建议按高优先级处置"。
- **阿里云**："利用该漏洞需要使用受影响的 files 会话存储处理器，且攻击者能够影响会话数据并使文件写入在特定位置中断；**会话上传进度是输入途径之一，不能仅凭未开启上传进度功能就排除风险**。"

**我方判断**

- ⭐⭐⭐ **这条最重要的价值不是"又一个 PHP 漏洞"，而是它给了库内那条挂了三期未回填的硬缺口一个可执行的判定条件**。库内 11-17 的 [PHP 反序列化条目](./phpDeserializationProbe-2026-11.md) 第 7 段写着"我方 PHP 依赖清单 + `unserialize()` 入口清单 / 源源站自查 🔴 仍未回填" —— 那时它只能是一个**抽象待办**，因为"反序列化"指向应用代码，而应用代码在哪、有哪些、谁维护，库内无从得知。**本条把风险面从"应用代码"移到了"解释器默认配置"**：判定条件收敛为三条可机械核对的事实（**PHP 版本号 / `session.save_handler` / `upload_progress` 是否开启**）。**这是一次"待决项从定性变定量"的典型** —— 库内 11 期以来大部分待决项都卡在"缺我方侧一手材料"，本条提供的是**一条能被一线运维在 10 分钟内核对完的检查表**。
- ⭐⭐⭐ **"10 月打过补丁仍然有洞"这条要单独强调，因为它是台账级的错误来源**。库内 11-16 已记的 [Siemens Node2Shell/PHP2Shell 条目](./icsa26316SiemensNode2Shell-2026-11.md) 里明确写着"通用库版本基线：PHP ≥8.2.35/8.3.36/8.4.27/8.5.12" —— **那条基线现在必须改写成"PHP2Shell 基线"与"phpAfterShell 基线"两套并存**，且后者**更严**（8.2.36/8.3.37/8.4.28/8.5.13）。**我方若沿用旧基线做版本合规检查，会系统性地把一批"已修 PHP2Shell"的服务器判成合规** —— 这是典型的"修了入口没修根因"陷阱（与库内 11-20 记录的 `agent-framework` 投毒条目"重装一遍不是修复手段"同一类思维）。
- ⭐⭐⭐ **"10 次即可命中"改变的是优先级论证，而不是"是否紧急"**。depthfirst 的 10 次命中 + CN-SEC 的"参考 PHP2Shell 披露后数小时内即被扫描利用的节奏"合起来说明：**这个漏洞从公开到大规模扫描的窗口可能很短**。虽然官方状态是"无在野利用"，但 **PHP2Shell 的前例（同族、同入口、10 月 20 日泄露、10 月 21 日紧急发布、随后即被在野利用）就是最强的时间窗参照**。我方正确的姿态是：**不等在野利用报告，直接按"零日级响应"处理 —— 因为我方连自己站点跑的是哪个 PHP 版本都还没查过，这个不确定性本身就是风险**。⚠️ 但**不得写成"已被在野利用"** —— 那是编造。
- ⭐⭐⭐ **"关掉上传进度只去掉最易利用的入口，不消除缺陷本身"这句话，决定了缓解方案的层级**。加上"`INI_PERDIR`、应用 `ini_set()` 覆盖不了"，可以得出一个很实际的结论：**这不能靠应用侧改代码兜住，必须落到运维层（改 php.ini / FPM 池配置 + 重启 worker）**。而"迁到 Redis / 数据库会话后端"才是根治 —— 但那是一个架构变更。⚠️ **我方三条对外 PHP 站点里，续费商城在 11-15 被探测 43 次/5h、品行者主站在 11-17 被反序列化规则命中 —— 攻击面最热的两个站点恰好都在 PHP 侧**，所以"这三个站点是否用文件型会话"是本次最该先问的一个问题。
- ⭐⭐ **库内 11-17 已记的"反序列化攻击类型不在 block / ignore 名单内 → 命中即落人工通道 → 未自动拉黑"这条处置链缺口，本条给了它一个具体的对手方**。此前库内对"反序列化"的理解是"PHP 应用层对象注入"；本条显示**连"应用层完全没写 unserialize()"的 PHP 站点也可能被反序列化打穿**（因为会话文件里的对象是 PHP 自己写进去的）。这意味着 **WAF 侧把 `Deserialization` 列为"需人工确认"是不够的** —— 至少要把"含 `PHP_SESSION_UPLOAD_PROGRESS` 字段的 multipart 请求"单列为一种可检测的探测形态，而不是等载荷长成 PHP 对象。
- ⭐ **"官方要 gadget 链、发现方说不要"这个分歧，我方处置必须按更严的那一侧**。CN-SEC 明确写"应用中不存在已知 gadget 链**不是推迟修补的安全理由**"，且研究团队的链还依赖一个**尚未公开细节的原生类内存破坏缺陷**（是否已在本次发布中修复，未明确说明）→ **这意味着"我方没有 gadget 链所以我方安全"这个论证在原理上不成立**：原生类的内存破坏缺陷不需要我方应用配合。**结论：按版本号修，不按"有没有 gadget 链"评估。**
- ⭐⭐ **主机侧监测项是这条唯一的可观测抓手**（multipart 上传伴随 worker 崩溃/OOM + 会话目录畸形文件）。库内 11-17 遗留的待决项"`collect.py` 继续补采 Payload / 规则 ID / 事件 ID / WAF 动作"说明库内 WAF 侧采集本身还有缺口 —— **对这条漏洞，WAF 侧基本采不到有效信号，监测必须落在主机侧**，这本身也是一条应当写进待决的结论。

## 七、总结输出

**一句话结论**：**phpAfterShell 把漏洞点从"应用代码里的 `unserialize()`"搬到了"PHP 解释器的默认文件会话处理器"—— 非原子写入 + 会话格式无校验 → 攻击者只需发 multipart 请求、10 次尝试即可让旧会话尾部被反序列化；而 10 月的 PHP2Shell 补丁完全不修它，所以我方库里那条 PHP 版本基线（≥8.2.35/8.3.36/8.4.27/8.5.12）必须拆成两套并以后者为准；虽未入 KEV、无在野利用，但按 PHP2Shell 从公开到在野仅隔数天的前例，我方应当先取回三站点的 PHP 版本与会话配置，而不是等在野报告。**
