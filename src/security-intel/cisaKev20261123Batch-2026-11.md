An unauthenticated path-traversal-to-RCE (CVSS 9.8) in the open-source medical-imaging annotation server: a crafted image parameter to PUT /datastore/image writes a file outside the datastore, and from there to code execution. … **In the default configuration the server runs with authentication disabled**, so treat any internet-exposed instance as a priority.」

## 四、概要提取

- ⭐⭐⭐ **库内首条「自主 AI 智能体发现并利用」的 KEV 漏洞**（MONAI Label，CVE-2026-133968）：Cairn 框架 AI agent 自主发现零日并武器化，**2026-09 起在野利用，比 11-20 公开披露早约两个月**；归因"中国关联行为体、中等置信、未识别具体组织"；受害方是高校服务器。
- ⭐⭐⭐ **库内首条「SSRF 进 KEV」**（N-able MailAssure，CVE-2026-134624）：LDAP 同步连接检查中的 SSRF，已认证高权限 API 用户可令服务端连任意内网主机端口并发送伪造数据；**厂商是在调查自家托管云被攻破时才发现该漏洞**。
- ⭐⭐⭐ **库内首条「处置动作 = 移除」的 KEV 条目**（Idunno AntiCsrf，CVE-2026-131914）：ASP.NET 防 CSRF 库，**已停服、无补丁、官方要求 discontinue use 并迁移**。
- ⭐⭐⭐ **三条均带「Forensic triage required per BOD 26-04」** —— 库内首次记录"KEV 条目还要求做取证分诊"这一处置维度。
- ⭐⭐ **到期日 11-26 / 11-26 / 11-27**（收录后 2–3 天）；**CWE 分别为 918 / 24 / 502**；**MONAI 修复版 0.8.6**（披露即有补丁）。
- ⭐⭐ **库内首次记录「NVD 与 CNA 评分差」**（AntiCsrf 9.8 vs 9.3；N-able 8.7 vs 9.3，两处均 NVD 更严）→ **台账必须记分数来源**。
- ⭐⭐ **库内首次出现「默认配置即关闭认证」的放大表述**（MONAI）→ **"默认配置"应成为暴露面自查的固定检查项**。
- ⭐⭐ **反序列化攻击线在库内已横跨 PHP（11-17 我方主站命中 Allow 未拦截）与 .NET（本期 AntiCsrf）两栈**；"写文件 → 被自动消费"链路在 phpAfterShell 与 MONAI 上同型。

## 五、主要观点

**原文主张**
- CISA：三条漏洞已有在野利用证据，联邦机构须在 11-26 / 11-27 前处置，并**额外要求取证分诊**。
- Security Affairs（引 Amazon Threat Intelligence）：MONAI Label 零日被自主 AI agent 发现并利用，自 2026-09 起在野利用，早于公开披露两个月；归因中国关联行为体、中等置信；修复版 0.8.6。
- Security Affairs（引 N-able）：N-able 在调查自家 MailAssure / SpamExperts 托管云被攻破过程中发现该 SSRF；仅确认单台自托管服务器受影响，**未确认是否为初始入侵途径**。
- Zero Hunt：AntiCsrf 库已停服无补丁，官方要求的动作是**移除该模块**；NVD 对两条漏洞的评分均严于 CNA。

**我方判断**
- ⭐⭐⭐ **MONAI 这条把库内一条悬了 6 天的线索闭合了，而且闭合的方式比预期更重**。库内 11-19 记 EPICS 时已经观察到"AI agent 在 4 小时内找出 4 个漏洞"，但当时只能写"无在野利用"。**本期这条把三段补齐了：AI 自主发现 → 自主武器化 → 已被官方认定为在野利用并进 KEV。** ⭐⭐⭐ **这意味着库内关于"AI 找漏洞"这条线的判断必须从"能力演示"升级为"已在产生实际攻击"** —— 而这个升级改变的是**时间尺度**：如果漏洞从被公开到被在野利用的窗口正在被 AI 压缩到"披露前两个月"这个量级，那么**任何依赖"公开披露后再补丁"的流程，其有效性都在下降**。⭐⭐ **对我方的可执行含义**：**"补丁窗口"这个概念本身要重估** —— 不是"收到 CVE 后多久打上"，而是"漏洞存在多久了"。→ **动作：安全台账需要记录"漏洞首次可被利用的时间"（越早越好），而不只是"我们何时知道它"。**
- ⭐⭐⭐ **N-able 这条是我方 SSRF 主线最需要的外部支撑，它把一个悬案变成了一个有优先级的待办**。库内 11-18 那份文档写得很克制：证明了"接口形态与 SSRF 入口同构"，但明确"**不是该接口可被用于 SSRF**"，并留下一句"**需代码审计确认目标地址是否受限**"。⭐⭐⭐ **本期这条给了那句待办一个外部锚点**：**SSRF 已经被 CISA 认定为在野利用类别并进入 KEV**（不再是"我们观测到的一种类型"，而是"已被确认大规模利用的攻击面"）。⭐⭐ **两侧证据至此对齐**：外部侧 = 官方定性；内部侧 = 我方接口面（`/preview/getCorsFile` 的 Base64 URL 参数，解码即完整远端 URL）。⭐⭐⭐ **动作：那条"代码审计确认目标地址是否受限"的待办，从"跟踪项"升为"有外部依据的 P0 审计项"** —— 审计范围已由库内 11-18 划定为"`/preview/` 路径族 + 全站 Base64-URL 参数"，可直接开工，不需要再论证必要性。⭐⭐ **但纪律不变**：**仍不得下"我方存在 SSRF 漏洞"结论**（样本目标全指我方自身主机、无源站响应码观测）；**该待办是"审计"，不是"确认漏洞存在"**。
- ⭐⭐⭐ **"移除"这个处置动作，对我方的挑战是依赖关系可见性，不是安全知识**。AntiCsrf 的处置逻辑很直白：这是一个已停服的防 CSRF 库，官方要求你把它从依赖里拿掉。⭐⭐ **问题在于："这个库被哪些项目引用"这个问题，在没有依赖清单的情况下无法回答** —— 而库内 11-19 已记录过一个同族问题（"SCA / SBOM 对运行时层漏洞完全失效"，CISA 官方亲口写 "JDKs and Java runtimes may not appear as separate entries in software inventories"）。⭐⭐⭐ **两条合起来指向同一个我方缺口：库内至今没有一份"运行时 + 依赖"清单，而这正是"移除一个库"这类处置动作的前置条件。** → **动作：与库内 11-19 已提的"运行时清单"待决项合并，升级为一份"依赖与运行时清单（谁引用了什么、哪些已停服）"** —— **它的第一版用途不是查漏洞，而是回答"能不能移除某个东西"**。
- ⭐⭐ **"Forensic triage required"这个标记，把库内对 KEV 条目的理解从"修复任务"改成了"取证 + 修复"两件事**。库内 11-24 已记 vCenter 的教训："补丁不撤销已被取走的 SAML 签名材料、伪造令牌还能绕 MFA" → **如果只做补丁不做取证，等于什么都没做**。⭐⭐⭐ **这直接改写台账的字段设计**：一个 KEV 条目的处置状态不能只有"已修复"，至少要能记"已取证分诊 / 已移除 / 已缓解 / 待处置"四种状态。⭐⭐ 而且这条正好补上库内 11-19、11-20、11-24 反复出现的一个观察：**很多漏洞的"修复"并不撤销已经发生的失陷**（vCenter 的 SAML 材料、agent-framework 11-20 的"被偷的是身份不是密钥"）—— **取证分诊不是 CISA 的额外要求，而是我方一直在吃的一个亏终于被官方写成流程**。
- ⭐⭐ **NVD 与 CNA 评分差这条，价值在"别用错分数排优先级"**。两处差异方向一致（NVD 更严），这不是巧合而是常态：NVD 会按 CVSS 规范重新评估，CNA 常给厂商自评。⭐⭐ **对护网/等保方向的补丁优先级排序影响是直接的**（同一条漏洞，8.7 与 9.3 在很多排序规则里落在不同的整改批次）。→ **动作：台账记分数时必须带来源字段**（NVD / 厂商 CNA / CISA），并且**排序用 NVD 主分**（这是 NVD 的角色定位），厂商分只作参考 —— 这条要写进方向级基线，否则每期评估都会重新纠结一遍。
- ⭐⭐ **"默认配置即关闭认证"这条看似小，其实指向一类我方可能没意识到的暴露面**。MONAI 默认关闭认证，所以"互联网可达"直接等于"无认证可达"。⭐⭐ **我方自身的系统有没有"默认配置下不安全"的开关？** 这是一个可以立刻自查的问题（比任何扫描都快）：**默认账号、默认口令、默认关闭鉴权、默认监听 0.0.0.0** —— **这四项应该成为我方发布流程与交付检查单上的固定条目**。⭐⭐ 库内 11-16 已记的 DER 暴露面论文说"大量系统由安装商/终端用户配置"，讲的是**配置泛滥**；这条讲的是**默认值即不安全** —— 两者是不同的问题，需要不同的检查。
- ⚠️ **必须保持的边界**：① **不得把 MONAI 归因写成"中国黑客组织攻击高校"**（中等置信、未识别具体组织）；② **不得把 MONAI 的高校受害场景与我方 OT/能源业务关联**（无依据）；③ **不得下"我方存在 SSRF 漏洞"结论**；④ **N-able 未确认该漏洞为初始入侵途径**，不得改写；⑤ **三条我方一条都不用装 → 不得落"我方受影响"**；⑥ **本批次无一条进入"我方需立即修补"**。

## 七、总结输出

**一句话结论**：**CISA KEV 11-23/11-24 批次三条给库内补齐了三段此前悬空的链条 —— MONAI Label 是库内首条"自主 AI 智能体发现并利用"且早在披露前两个月即在野利用的 KEV 漏洞（这直接重估我方"补丁窗口"的时间尺度）、N-able MailAssure SSRF 让库内 SSRF 主线首次拿到官方定性（与我方 `/preview/getCorsFile` 的 Base64 URL 参数面内外证据对齐，11-18 那条代码审计待办由此升为有依据的 P0 项）、Idunno AntiCsrf 首次给出"移除而非修补"的处置口径（而这要求一份依赖与运行时清单）；三条还共同带来一个新的处置维度：KEV 条目要求取证分诊，"打了补丁"不等于"做了处置"。**
