## 四、概要提取

- ⭐⭐⭐ **CISA 于 2026-11-20 一天内收录四条 KEV，联邦期限统一 2026-11-23（72 小时）**；KEV 目录版本 2026.11.20、总数 1,790，前日 1,786 —— **差值恰为 4，算术自洽核对通过**。
- ⭐⭐⭐ **四条的唯一共同失效点是"认证边界本身失效"** —— 跨产品、跨厂商、跨评分（6.5 至 9.8）：vCenter 是 SRP 会话密钥泄露、Roller 是"解析器先于鉴权运行"、Expressway 是硬编码凭据、NetWeaver 是 JNDI 注入。
- ⭐⭐⭐ **vCenter CVE-2026-123890 被归因为 ARMORY CASTLE（前 UNC5221）的间谍活动，自 2026-09 初起作零日利用，早于 Broadcom 补丁两个多月**；CISA 在披露次日（11-20）入 KEV，期限再给 72 小时（11-23）。⚠️ 归因是 Mandiant/GTIG 的评估，Broadcom 未确认在野利用。
- ⭐⭐⭐ **Roller CVE-2026-129448 是 CWE-502，"XML-RPC 在鉴权前反序列化 vendor extension 类型"** —— 与库内 11-17 我方主站命中 PHP 反序列化规则（Allow 未拦截）**构成同一失效模式在两种语言里的互证**，但**不是同一产品，不得直接套用**。
- ⭐⭐⭐ **vCenter 的完整攻击链已被公开复现到工具级**：BONESAW（偷 `data.mdb` + 夺 SAML STS 签名私钥 + 建 SSO 管理员）、SAWSNAKE（**Golden SAML 伪造令牌，绕过 MFA**）、BEARBONES（带后门 Dropbear SSH，监听 **TCP 33992**）、LAZYBONES（**以 Slack 为 C2** 的 Go 后门）；入侵起点是另一个已在 KEV 的产品 BeyondTrust CVE-2026-102764，落点是**没有 EDR 的 Linux appliance**。
- ⭐⭐ **暴露面判定条件极清晰**：vCenter **可达 TCP 2012 即完全沦陷、无需任何凭据**；Expressway **仅集群部署受影响、单机不受影响**，修复 X15.5.20、X14 及以下需迁移；vCenter **7.0 无公开修复**且 **Quick Patch 不能用**。
- ⭐⭐ **本批次唯一给出的具体可检索 IOC**：`wombat@127.0.0.1`（出现在 `erlang.log`）与 `/mnt/harddisk/` 下的 Python 脚本。
- ⭐⭐ **Roller 暴露一条方法论级陷阱**：同一漏洞先以 CVE-2026-82384（仅列 6.1.5）发布，2026-11-17 又以 CVE-2026-129448 重发（覆盖 4.0.0–6.1.4）—— **只盯一个 CVE 号会漏掉整段版本区间**。
- ⭐⭐ **Roller 暴露"管理界面关掉开关不等于防住"**：官方明说旧版本**在检查该设置之前就已反序列化**，有效变通是改 `WEB-INF/web.xml` 的 `enabledForExtensions=false` 或移除 `/roller-services/xmlrpc` servlet 映射。
- ⭐ **SAP NetWeaver CVE-2025-42884 是 2025-11-11 补丁日的缺陷，一年后才入 KEV** → **"KEV 收录滞后一年是常态"**，不能把"不在 KEV 里"当作安全判据。
- ⚠️ **我方无 vCenter / Expressway / Roller / NetWeaver 的使用证据** → **不得下"我方受影响"结论**。

## 五、主要观点

**原文主张**

- **CISA KEV 条目页（Roller）**："allows an unauthenticated remote attacker to execute arbitrary code via the XML-RPC endpoint, which accepts and deserializes vendor extension types **before authenticating the requester**"；Forensic triage required：**Yes**。
- **worldprogramming**："These four… share one thing: in each, **the authentication boundary itself is what fails**."；"more than **two months** between the patch and the first known intrusion"；"SAP… A defect from SAP note 3660969 on the 11 November 2025 patch day reached KEV **a year later**."
- **Suriq（vCenter）**："The patch stops the next unauthenticated session key leak. **It does nothing to what was already taken.**"；"**exploitation is ongoing since September; patch was only released in November — many orgs likely still exposed**"。
- **HelixML（Roller）**："**Disabling XML-RPC in the administration UI is not enough**, because older versions deserialize the request before checking that setting."

**我方判断**

- ⭐⭐⭐ **本批次对我方的价值不在四条漏洞本身（都不在我方栈内），而在三条可迁移的方法论**：
  1. ⭐⭐⭐ **"认证边界本身失效"是一个比"RCE"更准的分类维度**。库内 11 期安全分析里，条目基本按"产品 + CVE"组织，导致每条都像孤例。而这四条跨四种产品、跨 6.5–9.8 评分，却共享同一失效结构：**不是"某个功能有洞"，而是"认证这一步被绕过"**。这直接印证了库内 11-19 建的 [攻击手法→防线覆盖度对照](../deliverables/remediation-defenseTacticCoverage-20261112.md) 应当**增加一个"认证边界绕过"手法族** —— 我方的防线里有"身份认证"这一层，但此前没有把它作为一个**可被单独绕过的边界**来对照。
  2. ⭐⭐⭐ **"补丁不撤销已被拿走的东西"这条原则，库内 11-20 刚在 `agent-framework` 条目上建立过**（"被偷的是身份不是密钥 → 轮换密钥无效，必须撤销信任关系"）。**vCenter 案例是同一原则的第二个独立案例，而且更极端**：vCenter 的 SAML STS 签名私钥一旦被取走，**攻击者可在任何时候、任意台服务器上铸造合法管理员令牌，绕过 MFA** —— 这意味着"补上补丁并轮换了管理员密码"**完全无效**。**两条独立来源在同一周给出同一结论 → 该原则应从"个案的处置建议"升级为"方向级基线条目"**。
  3. ⭐⭐⭐ **"配置失效型缓解"是一类必须单独识别的失效模式**。Roller 明说"管理界面里关掉 XML-RPC 不够，因为旧版本在检查该设置之前就已反序列化"。这与库内 11-20 的 `agent-framework`（"pip 优先用本地缓存不回源 → 缓存不清等于没修"）、11-19 的 Java4Shell（"`-XX:UseAVX=2` 在 ARM64 上会让 JVM 直接起不来 → 架构未知时只能用 `-XX:-UseBASE64Intrinsics`"）是同一类：**缓解措施本身有一个前置条件，不满足时它看起来生效、实际无效**。库内至今没有"缓解措施有效性前置条件"这个字段 —— **建议新增**。
- ⭐⭐⭐ **Roller 的双 CVE 编号，对库内"运行时清单"这条挂了两期的待决项是一个教科书级的补强**。库内 11-19 已记 Java4Shell 案例：CISA 官方亲口写 "JDKs and Java runtimes may not appear as separate entries in software inventories" → 得出"**组件清单不够，要运行时清单**"的结论，**且这项待决已从"体系盲区"升级为"现实暴露"**。Roller 给出的是**第二个维度**：**清单不仅要覆盖运行时，还要覆盖"同一漏洞的不同 CVE 号"** —— CVE-2026-82384（9 月，仅列 6.1.5）与 CVE-2026-129448（11 月，覆盖 4.0.0–6.1.4）是同一缺陷，**只扫一个号会漏掉整段版本区间**。库内 11-19 已记"我方 MCP Server 类漏洞"那条同类问题（"Mendix 7782 非回环 + 缺 Origin 校验"），当时讨论的是"端口维度"，**这里补上的是"CVE 号维度"**。
- ⭐⭐ **Expressway 的适用条件之精确，值得抄成一条采集纪律**："仅集群部署受影响、单机部署不受影响" —— 如果我方只按产品名做暴露面判断，就会误报或漏报。**我方库内的 [EPICS 工控漏洞条目](./epicsDerExposure-2026-11.md) 里记的 "PowerSYSTEM Center · 2 个 CVE"、[Siemens 五条通告](./icsa26316SiemensNode2Shell-2026-11.md) 里记的 "Spectrum Power/Energy Engage/blueplanet/bt-monitoring-vm"，都存在同样问题：产品级匹配 ≠ 部署级适用**。库内应当为每个安全条目补一个"**适用部署形态**"字段。
- ⭐⭐ **"零日先被利用、补丁后出"（vCenter）与"PoC 先出现、再被利用"（Expressway）是两种截然不同的时间序，处置方式也不同**。前者说明"**厂商公告发布日 ≠ 攻击开始日**"，我方的补丁窗口必须从"**攻击可能已开始**"倒推，而不是从"公告日"起算 —— 库内 11-16 已记 Siemens 条目"上游 10-21 修复、CISA 11-12 才发 OT 通告（滞后 22 天）"是同一问题的另一个面。后者说明"**PoC 公开日即攻击开始日**"。**这两种时间序应在我方"护网/补丁优先级"基线里分开处理。**
- ⭐ **SAP 那条给了一条反直觉但重要的观察：KEV 收录滞后漏洞公布整整一年是常态**。所以我方**不能把"不在 KEV 里"当作"未被利用"的证据** —— 库内 11-16 已记 CISA 五部门联合警告那条时我方结论是"官方定性核心是 unpatched **or internet-accessible**"，**"联网"才是核心**；这条正好补上了"KEV 滞后"这一维：**从我方视角看，真正的风险指标是"我方资产是否联网 + 是否在受影响版本区间"，而不是"它在不在 KEV 里"**。
- ⭐⭐ **唯一一条能立刻落成检测动作的是 Expressway 的 IOC**（`wombat@127.0.0.1` 出现在 `erlang.log`、`/mnt/harddisk/` 下的 Python 脚本）。**但我方无 Expressway 集群** → 正确用法是**把这条 IOC 作为"资产台账里若出现 Erlang 集群类设备时的检索模板"存档**，而不是现在就去做全网检索。

## 七、总结输出

**一句话结论**：**这四条我方一条都不用装，但它们共享的失效结构值得入库 —— 跨产品跨评分唯一的共同点是"认证边界本身失效"，其中 vCenter 证明了"补丁不撤销已被取走的 SAML 签名材料、伪造令牌还能绕 MFA"，与库内 11-20 的"被偷的是身份不是密钥"构成同一原则的第二个独立案例；Roller 证明了"管理界面里关掉开关不足以防住"和"同一漏洞两个 CVE 号会漏掉整段版本区间"；Expressway 证明了"产品级匹配 ≠ 部署级适用"；SAP 证明了"KEV 收录滞后一年是常态，所以真正的风险判据是联网可达 + 版本区间，而不是在不在 KEV 里"。**
