## 五、主要观点

**原文主张**

- SafeLine WAF 巡检报告（11-26 20:37 轮，v15.11）：9 个攻击源 IP；类型分布 🛡️ Threat Intelligence 7 / 📁 Info Leak 2；本轮新拉黑 2 个（`165.22.124.144` 置信度 0.98、`130.12.182.52` 置信度 0.94，均判为 `new_attack`、分类 scanner、模型 M3.1）；7 个 Threat Intelligence 走 fast-skip 默认忽略；白名单 56 个、变化 ±0；WAF 当前实际黑名单 199 个、本地备份 392 个（活跃 201、已删除 191）、本次新增 2、失败 0；今日新增合计 5 个 IP。
- 判定理由（LLM 原话）：`165.22.124.144` —— 「URL 明确探测 /.git/config 敏感配置文件，具有具体的信息泄露扫描特征」；`130.12.182.52` —— 「WAF 仅标记为泛化的 Info Leak，但 URL 明确探测 .env.swp 敏感配置文件且 **5 小时内重复访问**」。
- 拦截报文：两条均 **Deny**、站点均为兆瓦快链 `182.140.209.35:18443`，规则 `skynet_rule131091`（High）与 `skynet_rule65669`（Medium）。

**我方判断**

- ⭐⭐⭐ **本期最值得关注的不是「又拉黑了 2 个 IP」，而是报告格式本身的变化 —— 但这个变化必须被正确理解。** 库内 11-15 至 11-18 那批我方主站命中记录之所以一直「看不清」，正是因为报告当时只有类型分布、没有 URL 与动作；11-24/11-25 两期又因此把「缺字段」反复记成待办。**本期报告第一次把「哪条规则、什么动作、哪个站点、哪条路径、哪个事件 ID」全部给齐** —— **这意味着从本期起，我方第一次具备了对 WAF 事件做字段级对账与跨期关联的技术条件**。**关键在于必须立刻用它做一件事：把库内 11-15~11-18 的那批命中记录与本期这批放在一起比。** 库内 11-15/11-16/11-17/11-18 记的分别是 Info Leak **Allow**、反序列化 **Allow**、SSRF **Deny**、`policy_rule44` 误拦 —— **如果本期拿到的两条 Deny 能证明「同一站点、同一凭据收割族，路径在变而站点不变」，那我方就能第一次回答那个挂了四期的问题：「我方主站到底在被谁、用什么方式持续试探」**。
- ⭐⭐⭐ **「同站点跨期复发」这件事，比两条单次命中重要得多。** 库内 11-16 记的是兆瓦快链被 `/.env.backup` + `/phpinfo.php` 探测；本期同一站点被 `/.git/config` + `/www/.env.swp` 探测。**路径在换、站点不变，这正是「有人持续在扫这一个站」的形态**，而不是「全网随机扫描恰好路过」。**「扫描器基础设施 3,158 实例 / 92 网段 → 单 IP 黑名单覆盖度 ≈ 0」（库内 11-16）这条结论在单 IP 层面已经成立；本期这条证据把它推到了「单站点」层面 —— 我方对某一个站点的持续攻击，其防护有效性同样不能靠单 IP 封禁来衡量。**
- ⭐⭐⭐ **「130.12.182.52：判定表 1 次 / 报文 24 次」这个内部矛盾，是本期最有价值的技术信号，因为它推翻的是一条库内已经写进多期文档的结论。** 库内 11-24 写「每个 IP 攻击次数几乎全为 1 次（低频单点探测）」，11-25 写「四个 IP 攻击次数均为 1 次 → 低频单点探测的特征在 11-25 继续」—— **本期证明这个判断至少在 11-26 不成立**：有一个 IP 在 5 小时内打了 24 次，判定器自己也说了「5 小时内重复访问」，但计数表仍然记 1 次。**这说明「攻击次数」字段在报告里记的不是总请求数，而是「聚合进本轮判定表的样本数」**。**如果我方继续把「1 次」当「低频」读，就会系统性地低估真实的攻击强度** —— **这是比任何单条攻击都更容易导致决策失误的错误**。**必须立刻纠正：报告中的「攻击次数」字段不得用于判断攻击强度，强度判据只能用「5h 累计」。**
- ⭐⭐⭐ **「fast-skip 的 7 个里有 3 个已在黑名单」这个观察，把库内 11-25 那条结论从「无可见度」推进到了「有可见度但无效」。** 库内 11-25 的判断是「零新增拉黑的成因是我方侧无可见度」；本期证据更精确：**不是没有可见度，是看见了、其中一部分早就拉黑过、而这批流量仍在到达**。**这意味着 WAF 的 Threat Intelligence 拦截确实在工作（我方站点没有被记为被攻击），但它挡住的只是「已知恶意 IP 的重复访问」，挡不住「新 IP 的首次访问」—— 而后者才是攻击者轮换 IP 的目的。** **我方对「黑名单 + 威胁情报」这套组合的有效性判断，必须从「拦截了多少次」改成「**首次访问的新 IP 有多少进来**」。** 这是本期唯一一条能直接改判据的安全域结论。
- ⭐⭐ **「本次新增 2 vs 今日新增 5」的第三次出现，应该升级为常设校验项而不是每期备注。** 库内 11-24（6 个窗口外补录）、11-25（1 个）、11-26（3 个）三期连续出现，**且本期差额最大（2 vs 5）**。**这已经不是偶发，是巡检脚本与黑名单备份之间的固定口径差**。**正确算法固定为：「窗口内新增 = 本次新增；当日新增 = 窗口内新增 + 窗口外补录」，两者必须分列，任何趋势图只能用窗口内新增**。本期基线变化（活跃 +5 / 总 +5 / 已删除 ±0）也印证了**这 5 个全部计入活跃侧** —— 补录进来的 IP 直接进活跃区，**没有经过活跃/已删除的回收流程**，**这本身是一个需要确认的台账问题**（补录 IP 是否应经过一次有效性复核）。
- ⭐⭐ **白名单连续四期零变化（56 ±0）这条负结论必须继续照记，不得因为「一直没问题」就停止记录。** 库内 11-24 已记「七天内豁免面规模零变化」，本期是同一现象的延续。**零变化对一个白名单来说既可能是「管理得当」也可能是「根本没人看」** —— **库内无材料可判断是哪种**，因此只能维持「待核实」，**不得写成「白名单管理良好」**。
- ⭐⭐⭐ **本期最该被记住的一句提醒：**库内 11-26 日报写的那句「**报告未记录我方站点命中 ≠ 我方零攻击**」，在本期得到了教科书级的印证 —— **本期报告记录了两条我方站点命中，且动作是 Deny（已拦截）**。**换句话说：如果这四期（11-24~11-26）报告都「未记录命中」，我方就会得出「我方没被攻击」的错误结论，而实际上今天我方站点确实在被探测，只是恰好被拦住了。** **这条印证的是「否定证据不能替代观测」这个方法论，不是「我方被攻击了」** —— **不得写成我方存在漏洞**。
- ⭐ **`collect.py` 的改善是真的，但不能说「缺口已闭合」。** 本期它第一次给出了 `verdict` / `confidence` / `judge_model` / `severity` —— **这是库内 11-17 以来一直挂着的待办的第一块砖**。但 `source_url` 三条全空（脚本硬编码）、源 IP 全集、黑名单增减、白名单变化、窗口口径仍然缺。**更重要的是：这六项缺口里有五项是**报告里本来就有**的**（只有 `source_url` 是真的没有）→ **说明这不是「报告没有数据」，而是「脚本没把报告里的数据取出来」** → **补齐这五项是纯粹的解析工作，不需要任何外部配合，一两天可完成**。**这条待办的性质应当从「采集能力缺失」改写为「解析实现缺失」，责任归属与优先级都不同。**
