## 采集口径

安全情报最大的陷阱是**数量淹没优先级**。本域强制用"暴露面"过滤：

```
漏洞/CVE/攻击事件 → 是否打在我方真实暴露面上？→ 是 → 进整改规划
                                                  否 → 仅存档
```

判定"是否在暴露面上"的三问：
1. 用到的组件是否在我方技术栈里？
2. 若在，是**对外暴露**还是内网？
3. 暴露端口/路径是否可达？

三问全过才允许进 `deliverables/` 的专项整改。

### 四条采集线

| 采集线 | 来源 | 产出 |
|---|---|---|
| **CVE 跟踪** | GitHub Advisory / NVD / 厂商公告 | 漏洞影响面判定表 |
| **攻击面动态** | SafeLine WAF 巡检报告（内部） | 攻击类型趋势 + 真实攻击者画像 |
| **合规基线** | 等保 2.0 / 关基保护 / 数据安全法 | 基线差距清单 |
| **内部安全动态** | 巡检发现的暴露面问题（如备份文件残留） | 直接转专项整改 |
| **攻防覆盖度对照** | 公开披露的攻击手法（工控 CVE / 行业综述）+ 我方 WAF 观测 | 手法 × 我方防线覆盖度表 |

### 内部数据源（本域最有价值的部分）

外部漏洞新闻满天飞，但**我们自己的 WAF 日志是唯一"真实攻击者正在打我们"的证据**：

| 数据源 | 位置 | 提供什么 |
|---|---|---|
| WAF 巡检报告 | `~/.openclaw/workspace/waf-inspection-report-latest.md` | 攻击类型分布、被拉黑 IP、误报分析 |
| 攻击类型趋势 | 巡检报告归档 `waf-inspection-reports/` | 哪类攻击在涨、哪些 IP 段在反复试探 |
| CVE 监控 | `cvewatch` skill | 高危漏洞 vs 本地 watchlist 比对 |

| 信号 | 联动态 |

## 每条安全情报的落库格式

**统一用 [七段式文章结构](../meta/pipeline.md)**，安全域额外要求：

- 第 1 段信源核实：安全情报**必须至少两个独立信源**（CISA 官方通告 + 第三方分析），单一信源不采信
- 第 2 段事实核查：**CVSS 分数要核 v3.1 与 v4.0 两套口径**（很多报道只抄一个）；CVE 编号、受影响版本、修复版本逐个核
- 第 3 段快照：优先抓 **CISA 官方通告页**
- 第 5 段「我方判断」必须明确写**暴露面判定结论**（在暴露面 / 不在暴露面 + 依据）
- 第 7 段：只有在暴露面的才能勾选「专项整改」
