# 对外站点暴露面专项自查（.svn 残留 / 备份文件）

> 类型：**专项整改工作规划** · 优先级：**P0** · 责任人：\<待指派\>
> 来源情报：[EPICS 工控漏洞 + 光伏 DER 暴露面研究](../security-intel/epicsDerExposure-2026-11.md)
> 提出日期：2026-11-12 · 评审状态：待评审

## 1. 背景与证据

**内部 WAF 实测（2026-11-11 ~ 11-12）**：

| 攻击源 | 目标 | 行为 | 频次 |
|---|---|---|---|
| `45.138.12.51` | `https://182.140.209.35:18443/.svn/entries` | 探测 SVN 元数据目录 | **28 次 / 5 小时** |
| `42.92.x.x`（整段 16 个 IP） | `idmo.pinnenger.com:11443` | 批量探测 `/wwwroot.zip` `/webs.rar` `/webapps.zip` `/php.zip` `/web.tar.gz` `/pinnenger.com.sql` `/pinnengercom.sql` 等 | 集中爆发 |

**外部研究（2026-09）**：学术界对并网光伏 DER 的互联网规模评估显示，**大量光伏逆变器与监控平台因安装商/终端用户配置而直接暴露公网，其真实暴露规模此前被严重低估**。攻击者正在系统性地寻找运维遗留的凭据与配置。

**为什么这是 P0 而不是"顺手看一眼"**：

1. `.svn/entries` 被探测 28 次，说明**扫描者确信这类路径存在**（否则不会重复试）—— 但 WAF 拦住了请求，**不代表源站没有这个目录**
2. SVN 1.7+ 服务端默认不再保留 `.svn/`，但**老版本工作副本升级后可能残留**，且残留即可还原完整源码与提交历史（含数据库口令、第三方 API Key）
3. 备份文件扫描（`.zip`/`.rar`/`.sql`/`.tar.gz`）打的是**站点根目录**和**应用目录**，命中即可直接下载源码与数据库转储 —— 这是比漏洞利用更低门槛的入侵路径
4. 攻击源 `42.92.0.0/16` 已被整段拉黑，但**扫描行为本身不会停止**，换个网段就会回来

> ⚠️ **WAF 全程 Deny 不等于源站干净。** 这次三件事必须落到源站上确认，不能停在 WAF 层。

**额外发现 —— PTM 后端异常处理不当**：

`49.73.18.161` 命中规则 `m_response`，目标 `ptm.pinnenger.com:1443/itps/ptm/allocation/logisticsFileDownLoad`，风险等级 High，2 次命中。

`m_response` 的含义是**攻击点在 HTTP 响应内容里**（如 SQL 异常堆栈），**不是攻击者在攻击** —— 这更像**后端接口在异常时把 SQL 错误堆栈直接吐给了客户端**。请求侧取证无意义，需要用事件 ID `1e3ccc0d8744487c933807ab0e0956d2` 在 WAF UI 查完整响应内容。

## 3. 动作

### 阶段一：自查（Day 1–2）

- [ ] **全站 `.svn` 残留排查**：对每个对外站点（域名 + 端口）检查 `.svn/` 目录是否存在
  - 命令：`find / -type d -name ".svn" -not -path "*/node_modules/*" 2>/dev/null`
  - Web 可达性验证：`curl -sk https://<host>:<port>/.svn/entries`
  - 若存在 → 立即删除，并把残留目录加入发布流程检查项
- [ ] **全站备份文件排查**：检查是否存在 `.zip`/`.rar`/`.sql`/`.tar.gz`/`.tar`/`.bak`/`.old` 等
  - 重点路径：站点根目录、Web 根目录、`/itps/` `/webapps/` 等应用目录、数据库备份目录
  - 扫描命令：`find /www /data /opt -type f \( -name "*.zip" -o -name "*.rar" -o -name "*.sql" -o -name "*.tar.gz" \) 2>/dev/null`
- [ ] **确认版本控制规范**：开发/部署流程中是否残留 `.svn`/`.git` 目录到生产？CI 部署产物是否包含 VCS 元数据？
- [ ] **PTM 响应内容取证**：用事件 ID 在 WAF UI 查 `logisticsFileDownLoad` 的完整响应，确认是否泄露 SQL 堆栈
- [ ] **后端异常处理检查**：全量扫描各接口的异常返回，确认不会把 SQL 错误、堆栈、内部路径直接返回给客户端

### 阶段二：修复（Day 3–5）

- [ ] 清理所有 `.svn`/`.git` 残留与备份文件
- [ ] 后端统一异常处理：SQL/内部异常一律返回统一错误码与友好提示，详细日志只进服务端
- [ ] 错误响应回归测试：构造异常场景，验证响应体不含 SQL 语句、堆栈、内部主机名/路径

### 阶段三：固化（Day 6–10）

- [ ] **发布流程加自动检查**：部署产物打包后自动扫描 `.svn`/`.git`/备份文件，命中则阻断发布
- [ ] **WAF 规则加固**：对 `/.svn/` `/backup/` `.sql` 等路径组合加拦截规则（不只是单 IP 黑名单）
- [ ] 纳入日常巡检：把"备份文件/版本控制目录探测"作为攻击类型趋势项长期监控

### 不做什么（划边界）

- ❌ 不做渗透测试（本次是自查与加固，不涉及主动攻击）
- ❌ 不改各应用的业务逻辑（只改异常处理与部署流程）
- ❌ 不动 WAF 现有黑名单策略（另议）

## 4. 验收标准

- [ ] 全部对外站点 Web 可达性探测 `/.svn/entries` 返回 404/403，**无一例外**
- [ ] 全站扫描无 `.zip`/`.rar`/`.sql`/`.tar.gz` 备份文件残留
- [ ] PTM `logisticsFileDownLoad` 异常场景下响应体**不含** SQL 语句、堆栈、内部路径
- [ ] 发布流程检查已生效：构造一个含 `.svn` 的产物，**部署被阻断**
- [ ] WAF 已加规则：`.svn` 与备份文件路径组合被拦截（用测试请求验证）
- [ ] 全部检查项有书面结论与执行记录（不是"已检查没问题"）

## 6. 风险与依赖

- **风险**：备份文件可能不在 Web 根目录，而在应用读取的固定路径 → 排查需覆盖应用配置而非只扫站点目录
- **风险**：`.svn` 残留可能在容器镜像层内 → 需进容器查，而非只在宿主机查
- **依赖**：需要各站点的服务器访问权限与部署流程负责人配合
- **风险**：清理后若无固化机制，下一次部署会重新引入 → **阶段三不可省**
