## 三类产物

| 产物 | 是什么 | 生命周期 | 判定标准 |
|---|---|---|---|
| **产品特性** | 新增/增强的产品能力，对外可见 | 进版本规划 | 客户能感知，或支撑合规硬性要求 |
| **需求变更** | 已有功能的行为调整（接口/字段/流程/默认值） | 进迭代 | 不改功能语义，但实现方式必须变 |
| **专项整改工作规划** | 一次性工程任务，有明确完成态 | 有截止日 | 消除一个具体风险或达标一个具体标准 |

**边界怎么划**：

```
要新增一个用户能用的新能力        → 产品特性
改了老功能的接口/字段/流程        → 需求变更
补一个漏洞/达标一条合规要求       → 专项整改规划
```

拿不准就问一句：**做完了客户会不会在界面上看见？** 会 → 产品特性或需求变更；不会 → 专项整改。

## 评审门槛

**情报进 `deliverables/` 前必须过这四关**，任一关不过就退回简报：

| 关卡 | 判据 | 不过怎么办 |
|---|---|---|
| **1. 影响可证** | 能指出我方**具体**受影响的产品线/系统/接口 | 退回"背景噪声" |
| **2. 动作明确** | 能写成一句"**要做什么**"，不是"要关注" | 退回简报继续观察 |
| **3. 归属明确** | 能落到某条产品线，且有明确责任人 | 挂起等组织确认归属 |
| **3′. 方向归属**（2026-11-12 起）| 能落到 **网络安全 / 信创 / 等保 / 隐私保护 / 护网** 五个方向之一 | 退回简报跟踪 |
| **4. 可验收** | 有可验证的完成标准（不是"加强防护"） | 退回，补验收标准 |

> 📌 **评审意见走 GitHub issue：一条意见一个 issue**，格式见 [review-question 模板](https://github.com/ishadowland/pv-intel/blob/main/.github/ISSUE_TEMPLATE/review-question.yml)（背景 → 一个问题 → 选项 → 影响面 → 关联文档）。收齐后结合意见更新文档再统一 close。

> 第 1 关是最容易放水的一关。**"可能会影响"不算影响**，必须能指名道姓。

> 📌 **本阶段口径（2026-11-12 用户明确）**
> - **转评审只走五个方向**：网络安全 · 信创 · 等保 · 隐私保护 · 护网
> - **暂不要求精到具体产品** —— 库内尚无各产品线"特性 / 功能 / 应用场景"的结构化材料，凭情报做产品对应会失真
> - 因此本阶段产物应是**方向级**的（基线 / 覆盖度 / 差距清单 / 演练场景），产品级归属待材料积累后启用
> - 产品线级产物一律标 🟡 **待复核**，不直接进排期

## 一份产物该有的样子

好的产物长这样：

> **组件价格预测接入估值模型**
> 类型：产品特性 · P1 · 责任人：张三
> 来源：[11 月第 2 周简报](../briefings/README.md)
> - 背景：组件价格在 11 月两周内跌 8%，我方电站资产估值模型仍用季度均价，导致资产账面值与市场偏离超 5%。
> - 动作：估值服务新增 `priceSource` 参数，支持接入实时/预测价格曲线；默认仍走季度均价。
> - 验收：传入 `priceSource=forecast` 时估值结果与预测曲线一致；回归用例覆盖两种模式。
> - 排期：设计 2 周 / 开发 3 周 / 上线随 R2026.12。

差的产物长这样：

> **加强组件价格风险监控** ❌ —— "加强"没有验收标准，"监控"没说监控什么，责任人空着。

## 评审节奏

| 周期 | 动作 | 产出 |
|---|---|---|
| 每周一 | 周报做评审预筛 | 候选清单 |
| 评审中 | **每条评审意见开一个 issue**（[评审问题列表](https://github.com/ishadowland/pv-intel/issues?q=is%3Aissue+label%3A%E8%AF%84%E5%AE%A1%E9%97%AE%E9%A2%98)） | 待决清单 |
| 意见收齐 | 结合意见更新文档 + 回写结论 | 文档更新 + issue 关闭 |
| 每月首个工作日 | 正式评审会，过门槛 | 本月产物定稿 + 排期 |
| 每月末 | 复盘上月产物落地情况 | 闭环率 |

**闭环率**是本域的核心指标：提出 → 排期 → 完成。低于 70% 说明不是产出不够，而是评审太松。
