2

3

公告给出的临时办法是在反向代理或 API 网关处阻断 POST /guardrails/test_custom_code。同时确认代理本身没有暴露在互联网上。

4

收紧管理员密钥并检查是否已泄露
公告称，在默认配置下访问该端点需要代理管理员凭证。请检查管理员密钥是否出现在共享聊天、代码或日志中；如有疑虑，请轮换该密钥（ 环境变量与 API 密钥基础 ）。

5

排查是否存在入侵迹象
在代理访问日志中，查找来自陌生时间或来源的 /guardrails/test_custom_code 调用。同时检查代理的子进程以及陌生的对外连接。据公告，默认 Docker 镜像中代理以 root 身份运行，因此如发现异常，请轮换代理保存的所有大模型服务商密钥，并逐一检查各服务商的使用记录（ 如何排查入侵 ）。

FAQ
Q 什么是 CVE-2026-40217？ A LiteLLM 代理中的 POST /guardrails/test_custom_code 会在一个自行实现的沙箱中运行用户提供的 Python 代码，该沙箱可通过字节码级技术逃逸。逃逸后，任意代码会在代理进程中运行，BerriAI 称默认 Docker 镜像中该进程以 root 身份运行。CVE 记录中的 CVSS v3.1 为 8.8。

Q 无需身份验证就能攻击吗？ A BerriAI 的公告称，在默认配置下访问该端点需要代理管理员凭证。CISA 的 KEV 描述只说明远程攻击者可以执行代码，并未涉及身份验证。CVE 记录的 CVSS 也假设需要低权限（PR:L）。本站认为，管理员密钥已泄露或管理员 API 暴露在互联网上的环境风险最高。

Q 哪些版本受影响，修复版本是什么？ A BerriAI 的公告（GHSA-wxxx-gvqv-xp7p）将 1.81.8 至 1.83.10 之前的版本列为受影响，并称已在 1.83.11 中修复；请升级到 1.83.11 或更高版本。该公告在首个修复版本上前后不一致（1.83.10 与 1.83.11），因此请以 1.83.11 或更高版本为目标。CVE 记录给出的是 LiteLLM 至 2026-04-08 为止，而非具体版本号。

Q 有临时缓解办法吗？ A 有。公告称，如果无法立即升级，可在反向代理或 API 网关处阻断 POST /guardrails/test_custom_code。这能关闭该入口，但不能替代修复。

Q 这与 10 月 LiteLLM 1.107.0 事件是同一件事吗？ A 不是。10 月 21 日的事件中，1.107.0 分发了恶意软件，属于对分发包的篡改（供应链攻击）。本漏洞是产品缺陷。需要注意：升级到 1.83.11 或更高版本时，不要选择有恶意的 1.107.0。详见我们的另一篇文章。
