「 所有 Java 用户都应该立即更新 ！」
近日，安全研究机构 Calif 发出警告。紧接着，美国网络安全和基础设施安全局（CISA）也在 11 月 18 日敦促 Java 用户尽快安装安全更新。
这次让众人如此紧张的，是一个名为 Java4Shell 的高危漏洞（CVE-2026-114938）被 Calif 披露了出来，其直接写道：“ 一次编写，RCE 四处运行。 ”根据 CVSS 4.0 标准，该漏洞的严重程度为 9.2 分（满分 10 分）。

光看名字，很容易让人想起 2021 年曾让无数开发者头疼的 Log4Shell。不过，两者其实并没有直接关系。这次的问题不在 Log4j，而是藏在 OpenJDK 底层的 Base64 解码优化实现中。
也正因为如此，想要彻底修复它，光更新某个应用的依赖库还不够，还得检查并升级实际运行的 Java 环境。
更麻烦的是，受影响的可能不只是 Java 本身。根据 Calif 公布的测试结果，Atlassian Jira、Confluence、Jenkins、JFrog Artifactory、Keycloak 等多款常见企业软件都可能成为攻击目标。在部分配置下，攻击者甚至不需要登录账号，就有机会实现远程代码执行。

一个 Base64 解码器，怎么就成了攻击入口？
先简单解释一下 Base64。
在日常开发中，Base64 是一种非常常见的数据编码方式，经常被用于身份认证、文件上传以及网络消息传输。例如，HTTP Basic Authentication、SAML 身份认证等场景，都可能涉及 Base64 数据的编码和解码。
为了提高处理速度，OpenJDK 在部分支持 AVX-512 VBMI 指令集的 x86-64 处理器上，专门使用了一套经过优化的 Base64 解码实现，可以一次处理更多数据。
问题恰恰出在这里。
Calif 研究人员发现，这段经过手工优化的底层汇编代码，在处理某些特殊构造的 Base64 字符串时，会错误计算输出数据的长度，导致数据被写入原本分配好的内存区域之外。
简单来说，就是程序本来只准备了一块固定大小的内存空间，结果解码器却往外多写了一截，把旁边的数据也给覆盖了。
这类问题在安全领域被称为堆缓冲区溢出，可能导致内存破坏、敏感信息泄露，严重时甚至可以被进一步利用，实现远程代码执行。
Calif 给出的触发方式甚至相当简单：只需要 64 个连续的字母 A，再加上一个等号，就能触发漏洞。
AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=

在较早的 OpenJDK 17 版本中，触发条件则是 128 个 A 后面跟一个等号。
更值得注意的是，即便 Java 最终识别出这段 Base64 数据不合法，并抛出异常，内存越界写入实际上也已经发生了。
也就是说，程序虽然拒绝了这段输入，但该造成的内存破坏已经造成了。

Confluence、Jira 等常用软件也中招了
Java4Shell 令人焦虑的地方，在于它并不局限于 Java 运行时本身。
由于漏洞位于 OpenJDK 的底层 Base64 解码实现中，任何调用相关解码接口、且满足特定运行条件的 Java 应用，都可能成为攻击入口。
Calif 公布的初步测试结果显示，以下软件均存在被利用的可能：
无需登录即可尝试远程代码执行：

Keycloak

Atlassian Jira

Atlassian Confluence

JFrog Artifactory

Jenkins

PingFederate

需要经过身份认证后才能利用：

Apache Kafka Broker

Apache Solr

Elasticsearch

Gerrit

Spinnaker

这份名单还不是完整名单。
Calif 还在基于 Apache Struts、Spring Boot 等常见框架构建的示例应用中成功实现了远程代码执行。
原因并不复杂：很多应用会在身份验证、文件上传等日常功能中调用 Base64 解码接口。如果这些处理发生在用户完成身份验证之前，攻击者就可能利用这一入口，在没有账号的情况下触发漏洞。
此外，研究人员还提到，Java 客户端程序也可能受到影响。例如，一个 Java 程序在连接攻击者控制的恶意服务器时，也可能因为处理相关数据而遭到攻击，即使它本身并没有对外开放服务。
当然，这并不意味着所有安装了 Java 的机器都能被直接攻破。
Java4Shell 的利用需要同时满足几个条件： 运行受影响的 Java 版本、使用支持 AVX-512 VBMI 的 x86-64 处理器，并且目标应用需要将攻击者可控的数据传递给存在问题的 Base64 解码路径。
而且，Calif 特别强调，这个漏洞并不存在一个可以直接攻击所有应用的通用利用程序。不同应用的内存分配方式和数据处理流程不同，攻击者需要针对具体应用构建不同的利用链。

AI 帮忙挖漏洞，Token 花费不到 200 美元
这次 Java4Shell 还有一个值得关注的细节：AI 在漏洞发现和利用过程中发挥了相当重要的作用。
根据 Calif 公布的技术报告，研究人员 Quang Luong 在审计 OpenJDK HotSpot JVM 时，将重点放在 JIT 编译器、底层 Intrinsics（内建函数）、常用 API 以及密码学相关代码上。
不过，这次并不是研究人员逐行手动检查代码。
他直接让 Codex 帮忙审计这些关键区域。
最初，AI 给出的不少结果并不靠谱，有些问题根本无法从外部触达，有些则需要极不现实的攻击条件。
但在持续调整提示词、筛选结果之后，Codex 最终找到了 Base64 解码器中的内存破坏问题。
随后，研究人员又利用 AI Agent 协助开发攻击链。
Calif 给出的数据是： 发现漏洞花了大约 1 小时，开发出第一个可用的漏洞利用程序又花了 2 小时，总 Token 成本不到 200 美元。

Oracle 火速发布补丁，其他 Java 发行版也要检查
漏洞公开后，Oracle 已于美国当地时间 11 月 17 日发布修复更新，OpenJDK 项目也同步发布了安全公告。
根据 Oracle 的安全公告，CVE-2026-114938 在 CVSS 3.1 评分体系下为 8.1 分。
需要注意的是，这次漏洞并不只影响 Oracle 自家的 Java。
由于问题存在于 OpenJDK 代码中，以下多个基于 OpenJDK 构建的 Java 发行版也可能受到影响，如 Amazon Corretto、Eclipse Temurin、Microsoft Build of OpenJDK、Azul Zulu、BellSoft Liberica、SAP SapMachine、Red Hat OpenJDK、Oracle OpenJDK 等。
Calif 指出， OpenJDK 17.0.6 及之后的版本可能受到影响。 不过，具体影响范围还需要结合处理器指令集和实际运行环境判断。
如果暂时无法升级，Calif 还给出了两种临时缓解方式：

使用 -XX:-UseBASE64Intrinsics，关闭 Base64 硬件加速解码实现。

使用 -XX:UseAVX=2，在 x86-64 环境下禁用 AVX-512 指令。

不过，这些方法只是临时缓解措施，不能代替正式安全更新。
对于 Java 开发者和运维人员来说，现在最重要的事情，就是检查服务器实际运行的 JDK 版本、CPU 指令集支持情况，以及 Jenkins、Jira 等关键服务背后的 Java 运行环境，尽快完成升级。
毕竟，谁也不希望一个原本只是为了加快 Base64 解码速度的优化，最后变成服务器被攻破的入口。
