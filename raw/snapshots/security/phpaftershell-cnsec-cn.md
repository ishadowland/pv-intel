PHP默认文件型会话处理器在更新会话时采用非原子写入机制，通过pwrite()与ftruncate()两次系统调用完成覆写，若进程在两次调用间被中断（如OOMKill），文件将残留新旧数据拼接。攻击者可利用 session.upload_progress 等入口构造长度字段，使旧数据尾部被解析为独立记录并触发反序列化，在存在可用gadget链的条件下实现远程代码执行。影响PHP 8.2至8.5多个版本，10月打过PHP2Shell补丁的服务器仍受影响，需升级至8.2.36/8.3.37/8.4.28/8.5.13及以上版本。

预警等级：严重（ Critical ， CVSS v4.0 9.2 ） 　｜　披露时间： 2026-11-19 　｜ 一句话结论： PHP 默认文件型会话处理器在更新会话时未先清空文件，写入被中断后新旧会话数据拼接，可被诱导反序列化出受控对象；在存在可用 gadget 链（或结合原生类内存破坏缺陷）的条件下可实现 RCE 。 10 月打过 PHP2Shell 补丁的服务器仍受影响，必须再次升级。

三、漏洞技术原理

3.1 会话文件的存储结构

PHP 默认以文件方式保存会话，每条记录由 “ 键名 + 序列化数据 ” 构成。序列化数据内部靠长度字段界定字符串边界，文件层面没有完整性校验、提交标记或结束标识。这意味着只要长度字段被重新解读，原有字符串中的字节就可能被切分成一条独立记录。

3.2 非原子写入（缺陷根因）

files 处理器在更新已有会话文件时，直接向原文件覆写，而不是先清空再写入；底层通过 pwrite() 与 ftruncate() 两次系统调用完成，二者组合不具备原子性。

若 PHP 工作进程在这两次调用之间终止（例如内存超限被 OOM Kill 、线程内硬内存限制触发等），文件会残留：

· 头部：新会话数据的起始部分；

· 尾部：旧会话数据未被覆盖的残余部分。

3.3 拼接污染与反序列化触发

攻击者通过可控的会话数据（典型入口是 session.upload_progress ）设定新数据中的长度字段，使原本无害地位于旧数据尾部的文本被解析为一条独立记录 —— 其中可包含被构造的序列化对象。下一次携带同一会话 ID 的请求调用 session_start() 时， PHP 按正常路径对该对象执行反序列化。

3.4 代码执行的最终条件

· 应用内存在可用的对象 gadget 链：反序列化对象在魔术方法调用链上触发危险行为，形成 RCE ；

· 研究团队公开的完整链未依赖应用侧 gadget ，而是结合了一个 PHP 原生类中的内存破坏缺陷完成执行；该原生缺陷细节尚处于协调披露阶段，是否已在本次发布中修复未明确说明；

· 即便不达成 RCE ，拼接污染也可在应用自身校验之前，篡改登录身份、权限标识或 CSRF Token 等普通会话值；会话数据同样可能被损坏。

3.5 修复后的行为

修复版本在每次写入前先清空会话文件，若清空步骤失败则中止写入。写入被中断时仍可能丢失会话数据，但不会再残留可被利用的旧数据尾部；同时新版默认关闭上传进度（ session.upload_progress.enabled ）。

四、攻击路径与利用前提

前置条件清单：

· session.save_handler = files （默认值）；

· session.upload_progress.enabled = On （修复前默认开启）；

· 攻击者持有 / 可控一个有效会话 ID ；

· 存在在写入中途杀掉 PHP worker 的手段（内存压力、请求时序、 Apache worker / cgroup 环境条件等）；

· 后续存在携带同一会话 ID 调用 session_start() 的请求；

· RCE 还需应用 gadget 链或另一原生内存破坏缺陷配合。

典型链路：

· 构造 multipart 上传请求； PHP 的 RFC 1867 上传进度回调在目标脚本执行前就打开会话文件并写入进度数据 —— 应用无需提供上传表单，端点也不必须主动调用 session_start() ；

· 在写入中途中断 worker ，制造新旧数据拼接的会话文件；

· 同会话 ID 发起后续请求,触发 session_start() 反序列化被植入的对象；

· 经 gadget 链 / 原生内存破坏缺陷在 worker 权限内执行代码，可读取或篡改应用所处理的数据、凭证与客户记录。

五、与 10 月 PHP2Shell 事件的关系

· PHP2Shell （ CVE-2026-109618 、 CVE-2026-109619 ）同样滥用上传进度回调，细节于 10 月 20 日泄露，次日紧急发布修复，后续已出现在野利用。

· 当时补丁限制了上传进度回调阶段可解析加载的类，但未改动会话文件的写入行为:对象数据仍会落盘,只是在回调阶段不被激活,到普通请求调用 session_start() 时才被反序列化激活。

· phpAfterShell 正是绕过这一限制、直击剩余的文件写入缺陷。研究团队版本比对显示, 10 月版本与 RC 版本只是把截断步骤在写入前后调换，并未消除 “ 残留旧尾部 ” 这一原语。

· 风险提示： 10 月仅升级到 8.2.35 / 8.3.36 / 8.4.27 / 8.5.12 的资产，必须按本公告再次升级。

六、风险研判

可达性与评级分歧：

· Depthfirst 认为默认配置即可达：文件会话是默认处理器，上传进度在修复前默认开启；

· PHP 官方在 11 月 18 日公告中表述其严重问题 “ 需要非默认配置或非常规环境 ” ，未就本 CVE 进一步说明；

· 客观上，竞态中断 worker 这一步在真实环境中存在操作摩擦，研究团队测试中新进程第 11 次尝试才进入正确文件状态 —— 该计数仅反映文件置态成功率，不等于代码执行成功率。

影响面判断：

· 暴露面集中在使用默认 files 会话、开启上传进度的 PHP Web 应用；

· 框架类型（ WordPress / Laravel 等）不改变本缺陷的暴露情况，差异仅在于是否存在现成 gadget 链；

· 当前无公开武器化利用、未入 KEV ，参考 PHP2Shell 披露后数小时内即被扫描利用的节奏，补丁扩散窗口期可能被自动化扫描与利用工具快速跟进，建议按高优先级处置。

七、处置建议

7.1 紧急处置（首选）

· 升级至对应分支修复版本： 8.2.36 / 8.3.37 / 8.4.28 / 8.5.13 / 8.6.0 ； PHP 8.1 及更早迁移到受支持分支。

· 升级后重启 PHP-FPM 或 Apache ，确保所有 worker 加载新二进制；容器环境重新构建镜像，不要依赖浮动标签。

· 核对实际对外提供服务的版本（ phpinfo() 或 php-fpm8.x -v ），不要只核对 CLI 版本。

7.2 临时缓解（暂不能升级时）

在 php.ini 或 FPM 池中设置：

session.upload_progress.enabled = 0

随后重启 PHP worker 。该指令为 INI_PERDIR ，应用代码中的 ini_set() 无法覆盖。

注意：这只是关闭最易利用的入口路径，并不消除缺陷本身； 应用若通过其他方式向会话写入攻击者可控数据，仍处于风险中。

· 将会话存储迁移到 Redis / 数据库等 “ 单次整体替换记录 ” 的存储后端。

· 收敛应用向会话中存放的不可信数据，避免把用户可控内容直接写入会话。

排查配置中是否存在显式重新开启该功能的设置：

grep -rn "session.upload_progress.enabled" /etc/php* /etc/httpd /etc/apache2 /etc/nginx

· 检查 php.ini 、发行版包、主机面板是否把上传进度重新置为 On—— 新版只是默认关闭，显式配置仍会开启攻击路径。

7.3 纵深防御

· 排查是否存在已知反序列化 gadget 链，梳理应用中可被魔术方法链利用的类；

· 限制 PHP worker 权限、按最小权限部署，降低 RCE 后的横向与数据泄露半径；

· 关注同批次 17 个修复项（其中 7 个 CVSS 9.2 严重），包括 PHP-FPM 请求走私（ CVE-2026-129289 ）、会话序列化器不匹配（ CVE-2026-115560 ）、多起 UAF 缺陷（ CVE-2026-129481 / 129182 / 129474 / 129496 ），一并纳入补丁评估。

八、自检清单

· 核对所有 Web 节点实际服务的 PHP 版本，识别受影响分支与版本

· 10 月仅打 PHP2Shell 补丁的资产，确认是否仍在受影响版本内

· 会话保存处理器类型（ files / Redis / DB ）

· session.upload_progress.enabled 配置位置与生效值

· 是否存在显式覆盖该默认值的 php.ini 、 FPM 池、虚拟主机或面板配置

· 应用向会话写入不可信数据的代码路径

· 会话存储后端在更新被截断时的行为评估

· 容器镜像基线版本与重建计划
